## 平台组成

SCUPI CSLAB 是实验室规模的私有云平台。平台可以分成五层：出口、交换、计算、控制和带外管理。

| 层次 | 设备 | 作用 |
|---|---|---|
| 出口 | Netcore N60 Pro 路由器，运行 ImmortalWrt | 连接校园网，提供 NAT、IPv6 接入、DNS 转发和无线网络。 |
| 交换 | H3C S5120V3-54S-EI 三层交换机 | 承担实验室内所有 VLAN 的二层转发和三层网关，是内网的中心。 |
| 计算 | host50 至 host54 五台物理服务器 | 运行 OpenStack 计算服务、GPU 虚拟机和 Cinder 存储后端。 |
| 控制 | host50 上的一台 libvirt 虚拟机 | 运行 OpenStack 控制面服务、数据库、消息队列和 Horizon。 |
| 带外 | 五台服务器的 BMC 管理口 | 独立于操作系统，用于远程开关机、查看硬件状态和打开远程控制台。 |

这五层以及它们之间的连线，在[网络架构图](topo.md)中按颜色标出，可以对照着看。

另有一台 TP-LINK TL-SG2024D 交换机作为边缘接入设备，工作在标准交换模式，只负责扩展有线端口，不参与 VLAN 和路由配置。

## 资源提供

- 两台双卡 GPU 虚拟机，名称分别为 `gpu_server_2x4090_1` 和 `gpu_server_2x4090_2`。每台配置 32 个 vCPU、64 GiB 内存和两张 NVIDIA GeForce RTX 4090，单卡显存 24 GiB。
- 三台 CPU 计算服务器 host52、host53、host54，每台提供 256 个硬件线程和约 512 GiB 内存，用于普通虚拟机。
- 两套基于本地磁盘的 Cinder 块存储后端，分别位于 host50 和 host51，每套卷组容量约 3.6 TiB。
- 一组 VLAN 和 VXLAN 网络，用于管理、GPU 实例、普通实例和项目隔离。

## 逻辑结构

平台用 OpenStack 管理计算、网络、存储和认证。控制面以容器方式部署在控制节点上，由 Pacemaker/Corosync 管理容器化服务的启停。核心组件包括：

- **Keystone**：身份认证和服务目录。所有 OpenStack API 调用先经过它换取令牌。
- **Horizon**：网页控制台，用户通过浏览器操作实例、网络和卷。
- **Nova**：计算服务，负责创建、调度和生命周期管理虚拟机。
- **Neutron**：网络服务，负责虚拟网络、子网、路由、安全组和浮动 IP。
- **Cinder**：块存储服务，负责卷的创建、挂载、快照和备份。
- **Glance**：镜像仓库，保存安装虚拟机用的系统模板。
- **Placement**：资源清单服务，记录每台宿主机还剩多少 vCPU、内存和 PCI 设备，供 Nova 调度使用。
- **MariaDB 和 RabbitMQ**：分别保存平台状态和传递服务之间的消息。

服务目录中还注册了 Heat、Octavia、Manila、Senlin、Masakari、Cyborg 等扩展服务。它们是否真正承载业务，要根据项目需求单独确认，不能只看服务目录里有没有名字。

## 注意事项

**控制面只有一台虚拟机。** 控制节点运行在 host50 上，平台没有第二台控制节点。Pacemaker/Corosync 可以管理本机容器化服务的启停，但不能在一台机器整体故障时接管控制面。host50 同时承载控制节点、GPU 虚拟机 2 和一套 Cinder 存储，这是平台最重要的单点。

**Cinder 的 `IPSAN` 是逻辑名称。** 它不代表机房里有一台独立的高可用 SAN 阵列。实际实现是 host50 和 host51 各自用本地磁盘建立 LVM 卷组，再通过 iSCSI 把逻辑卷导出。卷的可用性取决于它所在的那台宿主机。

**管理网和租户网是分开的。** 物理服务器、控制节点和 BMC 使用 172.16.23.0/24、172.16.24.0/24 等管理网段；GPU 和普通实例使用 172.16.33.0/24 等租户网段。跨网段访问由 H3C 交换机路由，出实验室才经过出口路由器。

**API 状态不等于虚拟机内部健康。** OpenStack 显示 `ACTIVE` 只说明控制面认为实例存在并且电源状态正常，不代表虚拟机里的操作系统、驱动或显卡工作正常。判断 GPU 实例是否可用，要登录实例执行 `nvidia-smi` 等检查。

## 维护重点

日常维护不需要每天盯着所有指标，但有几件事必须定期确认：

1. 控制面服务、数据库、消息队列和 Cinder 后端是否正常。
2. 五台宿主机的时间是否同步。时间偏差会导致 Cinder 心跳误判，进而把正常的卷服务标记为 down。
3. Cinder 卷所在磁盘是否有足够空间，thin pool 是否接近上限。
4. 备份是否真的能恢复，而不是只看备份服务是否在运行。
5. 管理入口是否只对授权人员开放，普通用户文档里是否混入了设备管理账号。
6. host50 上的控制节点、GPU 虚拟机 2 和存储是否受到影响。

这些检查的具体命令和顺序写在[运行与日常维护](maintenance.md)中。

## 备注

- 本手册不记录实时容量、实时占用率、实时链路速率和当前服务在线状态。如果需要这些数据时，可以按照维护章节的命令现场采集。
- 本手册不保存管理口令或设备账号；维护入口由管理员通过内部渠道交接。
- 本手册中的设备地址、VLAN 编号、端口用途、服务组件和目录结构等，变更后应同步更新。
- 涉及关机、重启、改网络、改存储、改认证的操作，先在[运行与日常维护](maintenance.md)中确认影响范围，再安排维护窗口。
