# 风险评估与问题上报

## 什么情况需要上报

不是所有问题都需要写报告。自己能按手册解决的操作问题，处理完即可；以下情况应该整理成文件上报：

- 可能影响多人、整台宿主机或整个平台的故障。
- 涉及数据丢失、数据损坏或无法恢复的备份。
- 涉及账号泄露、越权访问、扫描、攻击或其他安全事件。
- 涉及个人信息、未公开研究数据、保密项目数据的泄露、误传或误删。
- 反复出现、按常规方法无法定位的问题。
- 需要改网络、存储、认证、驱动或底层配置，超出日常维护范围。
- 硬件告警、磁盘故障、GPU 异常、RAID 降级。
- 现有架构的明显单点、容量瓶颈或合规风险。

上报的目的不是“把问题丢给别人”，而是把现场信息、影响范围和建议整理清楚，让负责人能在有限时间内做决定。

## 上报前先做什么

### 1. 确认问题仍然存在

先确认不是临时网络抖动、输错地址、账号未开通或操作失误。用最简单的步骤复现一次，记录发生时间。如果问题已经恢复，仍然要记录，因为反复出现的问题可能在下一次造成更大影响。

### 2. 保留现场

不要急着重启、重装、删除日志、清理磁盘或改配置。这些操作可能让问题消失，也可能让原因永远查不到。

需要保留的现场信息：

- 报错截图或完整文本。
- 命令、时间、执行账号、目标主机。
- 相关日志的起止时间和关键行。
- 网络拓扑、VLAN、IP、端口。
- 最近的变更记录：谁在什么时候改了什么。
- 影响范围：单用户、单实例、单主机、整个平台。

### 3. 判断影响范围

| 范围 | 例子 | 处理优先级 |
|---|---|---|
| 单用户 / 单环境 | 某个 Conda 环境损坏、某个文件传不上去 | 低，按常规支持处理。 |
| 单实例 / 单主机 | 一台 GPU 虚拟机无法启动、一台宿主机磁盘告警 | 中高，尽快处理。 |
| 多用户 / 核心服务 | 控制节点不可用、Cinder 后端故障、交换机上联中断 | 高，立即处理。 |
| 安全 / 数据 | 账号泄露、数据被删、备份不可恢复 | 紧急，立即上报。 |

影响范围决定上报速度。单用户问题可以按模板整理后发送；核心服务中断或安全事件要立即联系负责人，不要等报告写完。

### 4. 查一下已有记录

先看手册、常见问题、变更记录和之前的报告，确认不是已知问题。如果是已知问题，补充新的现象和时间，不要重复开一份完全相同的报告。

## 复现和记录

### 复现步骤

复现步骤要能让另一个人照着做，看到同样的现象。写清楚：

1. 从哪台机器、哪个账号开始。
2. 执行了哪条命令，或在界面上点了哪个按钮。
3. 期望看到什么。
4. 实际看到什么。
5. 是否可以稳定复现，间隔多久出现一次。

不要写“服务器坏了”“网络不通”这种没有信息量的描述。写成“从 172.16.34.4 执行 `ssh root@172.16.23.50`，5 秒后提示 `Connection timed out`，同一时间 `ping 172.16.23.50` 正常，连续三次结果一致”。

### 原始输出

命令输出比截图更有用。粘贴文本时保留完整报错和时间，不要只截最后一行。涉及以下内容时，先脱敏：

- 口令、密钥、令牌。
- 个人身份信息、学号、联系方式。
- 其他用户的文件名和目录。
- 内部地址如果报告要发给外部厂商，按需隐藏。

不要把整份凭据表、数据库密码或私钥贴进报告。需要提供时，用受控渠道单独传递。

### 日志和截图

日志要带时间范围。例如：

```bash
journalctl -u nova-compute --since "YYYY-MM-DD HH:MM" --until "YYYY-MM-DD HH:MM"
```

截图适合展示网页界面、控制台、交换机面板，但关键文字要同时贴出来。截图不要包含口令、令牌或他人隐私。

## 风险评估

风险描述要回答四个问题：

1. **发生了什么**：事实，不是猜测。
2. **影响什么**：用户、实例、主机、网络、存储、数据。
3. **可能造成什么后果**：停机、数据丢失、性能下降、安全暴露。
4. **有多大可能**：已经发生、可能发生、理论上可能。

可以用下面的等级：

| 等级 | 判断标准 | 响应建议 |
|---|---|---|
| 严重 | 平台或核心服务不可用，数据丢失或安全事件已经发生 | 立即上报，启动应急处理。 |
| 高 | 单台宿主机、单个存储后端或关键功能不可用，影响多人 | 当天上报，安排维护窗口。 |
| 中 | 单实例或单用户受影响，有替代方案 | 按计划处理。 |
| 低 | 使用咨询、文档问题、优化建议 | 记录后集中处理。 |

等级不是用来“显得严重”，而是帮助负责人排优先级。把低风险问题写成严重，会消耗处理资源；把严重问题写成低风险，会错过处理时机。

## 报告怎么写

一份可处理的报告包含：

```text
标题：一句话说明问题
发现时间：
发现人：
影响范围：
当前状态：
复现步骤：
期望结果：
实际结果：
原始输出：
已尝试的处理：
初步判断：
建议的整改方向：
需要谁决策：
```

标题要具体，例如“host51 的 cinder-volume 心跳间断，GPU 虚拟机 1 卷操作超时”，不要写“存储有问题”。

“初步判断”可以写假设，但要标明是假设，不要把猜测写成结论。例如“可能是 host51 时间偏差导致心跳过期，尚未确认”。这样负责人知道下一步要验证什么。

“建议的整改方向”可以给多个选项：

- 立即恢复：重启服务、切后端、回滚配置。
- 短期规避：限制新任务、迁移实例、停用故障节点。
- 长期修复：扩容、替换硬件、改架构、补监控。

每个选项写清楚代价和风险，不要只写“建议修复”。

## 使用 AI 辅助分析

AI 可以帮助整理日志、解释报错、生成排查步骤，但不能代替现场验证。使用时注意：

- 不要把口令、密钥、令牌、完整配置文件或用户隐私发给外部 AI 服务。
- AI 给出的命令先在测试环境或只读环境验证，不要直接在生产环境执行。
- AI 可能给出看似合理但实际错误的结论，必须用日志、配置和实验验证。
- 不要让 AI 工具自动修改系统、删除文件、配置代理或批量下载。
- 报告中如果使用了 AI 分析，标明哪些是 AI 推测、哪些是人工确认。

AI 适合做“把这段报错翻译成人话”“列出可能的排查方向”，不适合做“直接帮我修好”。

## 上报渠道

| 问题类型 | 上报对象 | 方式 |
|---|---|---|
| 日常使用、账号、权限 | 实验室管理员 | 邮件或实验室约定的沟通渠道。 |
| 设备故障、网络中断、存储异常 | 实验室管理员，必要时实验室负责人 | 立即消息 + 报告文件。 |
| 安全事件、数据泄露、账号被盗 | 实验室管理员和指导教师 | 立即上报，不要公开讨论。 |
| 需要采购、扩容、架构调整 | 实验室负责人 | 书面报告，附影响和预算。 |
| 厂商硬件故障 | 设备管理员和厂商支持 | 按保修流程，附 BMC 日志和序列号。 |

不要同时在多个群里刷屏，也不要把同一份报告反复发给不相关的人。选一个主渠道，把信息一次写清楚。

## 后续跟踪

报告发出后，记录：

- 谁接收、什么时候接收。
- 初步结论和处理计划。
- 需要补充的信息。
- 处理进度和完成时间。
- 验证结果和遗留问题。

问题解决后，更新手册和监控规则。如果同类问题反复出现，说明不是单次故障，而是架构、容量或流程问题，需要单独评估。

## 不要做的事

- 不要为了“让问题消失”而重启、重装、删日志或改配置。
- 不要隐瞒影响范围，尤其是数据丢失和安全事件。
- 不要在报告中写没有验证过的结论。
- 不要把责任推给个人，报告对事不对人。
- 不要把包含口令、密钥、用户隐私的报告发到公开渠道。
- 不要在没有回滚方案的情况下执行“修复”。

## 报告模板

```text
【标题】
（一句话，包含对象和现象）

【发现时间】
【发现人 / 联系方式】
【影响范围】
（单用户 / 单实例 / 单主机 / 多用户 / 整个平台）

【当前状态】
（仍然存在 / 已恢复 / 间歇出现 / 正在扩大）

【复现步骤】
1.
2.
3.

【期望结果】

【实际结果】
（完整报错，不要只写“失败”）

【原始输出】
（命令、日志、截图说明；敏感信息已脱敏）

【已尝试的处理】
（做了什么，结果如何）

【初步判断】
（事实 / 假设，分开写）

【建议的整改方向】
（立即恢复 / 短期规避 / 长期修复，附代价和风险）

【需要谁决策】
（管理员 / 指导教师 / 实验室负责人 / 厂商）
```
