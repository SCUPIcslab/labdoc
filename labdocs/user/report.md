# 问题上报

遇到自己无法解决的问题时，先按[常见疑难解答](faq.md)做基本检查，再把信息整理清楚交给管理员。好的上报能节省双方时间，也能避免问题被误判。

## 先判断问题类型

| 类型 | 例子 | 找谁 |
|---|---|---|
| 账号问题 | 账号未开通、密码忘记、账号被锁、需要权限 | 按[账号与权限](account.md)中的申请流程联系管理员。 |
| 使用问题 | 不会建 Conda 环境、不会指定 GPU、不会传文件 | 先查手册和常见问题；仍未解决再联系管理员或同学。 |
| 技术故障 | SSH 连不上、显卡消失、磁盘写满、实例无法启动 | 联系实验室管理员或指导教师。 |
| 安全事件 | 账号被盗、发现扫描或攻击、发现陌生进程/公钥、误删重要数据 | 立即联系管理员和指导教师，不要公开讨论或自行处理；先按[应急处置与上报](../safety/response.md)保留现场。 |

## 上报前先做三件事

1. **确认现象**：是只有自己遇到，还是同机其他人也遇到？换一台机器、换一个账号是否仍然出现？
2. **保留现场**：不要急着重启、重装、删除日志或改配置。先保存报错信息、命令输出和时间。
3. **尝试复现**：用最简单的步骤再执行一次，确认问题能稳定出现。如果只是偶发，记录发生的时间和操作。

这三步不是形式。很多问题在重启或删除文件后失去线索，管理员无法判断原因。

## 上报时提供什么

一条完整的问题描述应包含：

- **谁**：姓名、Linux 账号、使用的实例 IP。
- **什么时候**：问题首次出现的时间，是否持续到现在。
- **在哪里**：`172.16.33.91` 还是 `172.16.33.247`，是否在 Horizon 中操作。
- **做了什么**：执行了哪条命令、点了哪个按钮、改了哪个文件。
- **期望什么**：正常情况下应该看到什么。
- **实际什么**：实际报错、退出码、界面提示。
- **影响范围**：只有自己受影响，还是同机其他人也受影响；是否影响正在跑的实验。
- **已经试过什么**：按手册做了哪些检查，结果如何。

如果能提供命令输出，直接粘贴文本，不要只发截图。文本可以搜索、可以复制，管理员处理更快。截图适合展示网页界面或图形化报错，但要把关键文字一并贴出来。

## 常用诊断命令

根据问题类型，提前执行并保存以下输出：

```bash
# 基本信息
hostname
whoami
date

# 网络
ip -br addr
ip route
ping -c 4 172.16.33.1

# 显卡
nvidia-smi
nvidia-smi -L
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv

# 磁盘
df -h
lsblk
du -sh ~ 2>/dev/null

# 系统日志（只读最近部分）
journalctl --user -n 100 --no-pager
```

不要为了“清理现场”而删除日志、重装驱动或重建环境。这些操作会让问题更难定位。

## 上报模板

把下面的模板复制到邮件或消息中，按实际情况填写：

```text
【问题标题】一句话说明现象，例如“172.16.33.247 上 nvidia-smi 只显示一张卡”

姓名：
Linux 账号：
实例 IP：
发生时间：
是否可复现：
影响范围：

现象描述：
（正常应该怎样，实际怎样，完整报错）

复现步骤：
1.
2.
3.

已执行命令与输出：
（粘贴关键命令和原始输出）

已尝试的处理：
（按手册做过什么，结果如何）

是否影响他人任务：
（是/否/不确定，说明）

联系方式：
```

## 定级参考

| 级别 | 判断标准 | 例子 |
|---|---|---|
| 紧急 | 整个平台或整台 GPU 宿主机不可用，存在数据丢失或安全风险 | 所有实例无法访问、host50 宕机、发现账号被盗。 |
| 高 | 单台 GPU 虚拟机不可用，或关键功能缺失，无法继续实验 | 显卡消失、系统盘写满无法登录、实例无法启动。 |
| 中 | 单个用户或单个软件环境异常，有替代方案 | Conda 环境损坏、某个包装不上、文件传不上去。 |
| 低 | 使用咨询、文档错误、改进建议 | 命令不会用、手册某处写错、希望增加软件。 |

定级不是为了让问题显得严重，而是帮助管理员安排处理顺序。紧急问题可以直接联系管理员；非紧急问题按模板整理后发送，避免在多个渠道重复刷屏。

## 不要做的事

- 不要重启实例、宿主机、交换机或路由器来“试试看”。重启可能丢失证据和正在运行的任务。
- 不要重装系统、驱动或 Conda。重装会改变环境，可能让问题无法复现。
- 不要删除日志、清空目录或修改配置文件来“清理现场”。
- 不要 kill 别人的进程，也不要在管理员不知情的情况下结束共享服务。
- 不要自行清理疑似挖矿、木马或陌生公钥；先保留现场，按[应急处置与上报](../safety/response.md)处理。
- 不要在消息中发送密码、密钥或完整凭据表。
- 不要短时间内反复尝试错误密码，可能触发账号锁定。
- 不要把安全事件发到公开群聊或社交平台。

## 后续配合

管理员处理后可能会询问补充信息，或者要求你在维护窗口内配合测试。及时回复，说明操作结果。问题解决后，如果手册中的排查步骤不准确，可以反馈给管理员，帮助后续用户少走弯路。

如果问题反复出现，记录每次发生的时间、操作和现象。规律性的信息比单次报错更有价值。
