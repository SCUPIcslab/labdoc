# 常见疑难解答

遇到问题时先做三件事：确认自己登录的是哪台机器，确认显卡和磁盘的当前状态，保留完整的报错信息。很多“服务器坏了”其实是连错了 IP、显存被占满或系统盘写满。

```bash
hostname
nvidia-smi
df -h
```

把这三条命令的输出保存下来，后续排查和上报都会用到。

## TL; DR

| 现象 | 先检查 | 常见原因 |
|---|---|---|
| SSH 连接超时 | 是否在实验室局域网、IP 是否正确 | 不在实验室网络、IP 写错、网络不通。 |
| SSH 提示 `Permission denied` | 用户名、密码、账号是否开通 | 密码错误、账号未开通、用了项目账号。 |
| SSH 提示主机密钥变化 | 是否换过虚拟机或重装 | 服务器重装、IP 被重新分配。不要盲目删除 `known_hosts`。 |
| `nvidia-smi` 找不到命令 | 是否登录 GPU 虚拟机 | 登录到了 CPU 虚拟机，或驱动异常。 |
| `nvidia-smi` 只看到一张卡 | 是否有人直通或占用 | 显卡异常、虚拟机配置变化。 |
| `CUDA out of memory` | `nvidia-smi` 显存占用 | batch 太大、模型太大、残留进程。 |
| 两张卡都被占用 | `nvidia-smi` 进程列表 | 别人正在跑任务。等待或换卡，不要 kill 别人。 |
| `No space left on device` | `df -h`、`du -sh` | 系统盘或数据盘写满。 |
| `conda: command not found` | `which conda` | 没有初始化全局 Conda。 |
| `pip install` 权限不足 | 当前环境、是否在 base | 试图写系统目录，或没有激活自己的环境。 |
| 多卡训练比单卡还慢 | `nvidia-smi topo -m` | 没有 NVLink，通信开销大于并行收益。 |
| Horizon 显示 ACTIVE 但连不上 | 控制台、`ping` | 虚拟机内部系统或网络异常，不等于实例不存在。 |

## SSH 连不上

先确认三件事：

1. 电脑连接的是 `ImmortalWrt-2.4G`、`ImmortalWrt-5G` 或实验室有线网。
2. 登录地址是 `172.16.33.91` 或 `172.16.33.247`，不是 `172.16.23.x` 的管理地址。
3. 用户名是自己的 Linux 账号，不是 Horizon 的项目账号 `<项目账号>`。

然后测试网络：

```bash
ping 172.16.33.91
ssh -v <user_id>@172.16.33.91
```

`ssh -v` 会打印连接过程。如果卡在 `Connecting to ...`，是网络或防火墙问题；如果出现 `Permission denied`，是账号或密码问题；如果提示 `Connection refused`，是目标机器的 SSH 服务没有监听。

不要在短时间内反复尝试错误密码。多次失败可能触发安全策略，导致账号被锁定。确认密码大小写和输入法，仍然不行就联系管理员来重置密码。

### 主机密钥变化的提示

如果看到类似下面的提示：

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

说明服务器返回的 SSH 主机密钥和本地记录不一致。可能是服务器重装、IP 被重新分配，也可能是中间人攻击。不要直接执行 `ssh-keygen -R` 删除记录后继续登录。先联系管理员确认服务器是否重装或更换，再按管理员的指示更新 `known_hosts`。

## 登录后没有显卡

先确认自己登录的是 GPU 虚拟机：

```bash
hostname
nvidia-smi -L
```

`172.16.33.91` 和 `172.16.33.247` 才有 GPU。普通 CPU 虚拟机上没有显卡，`nvidia-smi` 报错是正常的。

如果确实在 GPU 虚拟机上，但 `nvidia-smi` 提示无法与驱动通信，可能是驱动或直通设备异常。不要自己重装驱动，保留完整报错并联系管理员。管理员需要在宿主机上检查 VFIO 直通和虚拟机配置。

## 显存不足

`CUDA out of memory` 表示显存不够。先看是谁占用了显存：

```bash
nvidia-smi
```

如果占用的是自己的残留进程，结束它：

```bash
kill <PID>
```

如果占用的是别人的进程，不要 kill。换另一张卡，或者等对方任务结束。也可以尝试减小 batch size、输入尺寸、模型并行度，或者使用混合精度训练。

不要用“把显存清理一下”的脚本强制释放别人的显存。显存由进程持有，强行清理会影响正在运行的任务。

## 显卡被占用

两张卡都可能被别人使用。启动任务前先看：

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
```

如果两张卡都有进程，等待或联系正在使用的同学。平台规定一张卡同一时间只跑一个任务，不要为了自己启动而结束别人的进程。

如果确认某张卡空闲，再用 `CUDA_VISIBLE_DEVICES` 指定它。不要不指定设备直接运行，程序可能默认占用所有可见显卡。

## 磁盘写满

先看是哪块盘满：

```bash
df -h
```

- `/` 满：系统盘满，影响登录和系统运行。优先清理家目录缓存、Conda 包缓存、pip 缓存和不再使用的环境。
- `/data` 满：数据盘满，影响数据集和检查点写入。清理自己的旧数据，或联系管理员扩容。

常用清理命令：

```bash
conda clean -a
pip cache purge
du -sh ~/.cache/*
du -sh ~/.conda/pkgs
```

删除前先 `ls` 确认路径。不要删除别人的文件，不要对不确定的目录执行 `rm -rf`。

如果系统盘已经满到无法登录，联系管理员从宿主机或控制台处理。不要自己重启虚拟机，重启不一定能释放空间，反而可能丢失未保存的工作。

可以参见 [服务器瓶颈排查](bottleneck.md) 了解如何判断服务器其他瓶颈问题。

## Conda 相关问题

### `conda: command not found`

先加载全局 Conda：

```bash
source /opt/miniconda3/etc/profile.d/conda.sh
conda --version
```

如果希望每次登录自动生效：

```bash
/opt/miniconda3/bin/conda init bash
source ~/.bashrc
```

不要因为找不到 Conda 就重新安装一套个人 Conda。服务器已经有全局版本，重复安装会占用家目录空间，也容易和全局环境冲突。

### `pip install` 报权限错误

先确认自己激活了个人环境：

```bash
conda activate myenv
which python
which pip
```

`which python` 应该指向 `/opt/miniconda3/envs/myenv/bin/python` 或你自己的环境路径，而不是 `/usr/bin/python`。如果指向系统 Python，说明环境没有激活。

不要用 `sudo pip install`。`sudo` 会把包装到系统目录，影响所有用户，也违反使用规范。需要用户级安装时，在自己的环境中执行 `pip install`。

### base 环境被改坏

如果有人在 `base` 中执行了 `conda update`、`conda install` 或 `pip install`，可能导致所有用户的默认环境异常。不要尝试自己修复 `base`，联系管理员处理。管理员可以从备份或其他节点恢复环境。

## 多卡训练比单卡慢

两张 4090 之间没有 NVLink，跨卡通信走 PCIe。多卡训练是否加速，取决于模型计算量和通信量。小模型、batch 很小、梯度同步频繁时，通信开销可能超过并行收益。

先看拓扑：

```bash
nvidia-smi topo -m
```

如果两张卡之间是 `SYS` 或 `PHB`，说明没有 NVLink，这是正常的。可以尝试：

- 增大单卡 batch size，减少同步频率。
- 使用梯度累积，减少跨卡通信次数。
- 使用混合精度，降低通信量。
- 如果模型不大，直接用单卡，避免多卡开销。
- 使用 `torchrun` 或 `accelerate` 的推荐配置，不要手工写错误的进程启动逻辑。

## Horizon 显示 ACTIVE 但连不上

OpenStack 的 `ACTIVE` 只表示控制面认为实例存在并且电源状态正常，不代表虚拟机内部操作系统一定健康。可能的原因包括：

- 虚拟机内部网络没有起来。
- 系统盘写满，SSH 服务无法启动。
- 虚拟机内部防火墙或 SSH 配置被改坏。
- 宿主机或存储异常。

先在 Horizon 中打开实例控制台，看是否能进入登录界面。如果控制台能看到系统但 SSH 不通，检查虚拟机内部网络和 SSH 服务。如果控制台也黑屏或卡住，联系管理员检查宿主机。

不要直接重启实例。重启可能丢失内存中的实验进度，也可能让问题更难复现。先保存能保存的信息，再联系管理员。

## 网络慢或下载失败

实验室网络带宽有限，以下行为会拖慢所有人：

- 大流量下载与实验无关的内容。
- 使用代理、内网穿透或翻墙工具。
- 多线程批量下载大量小文件。
- 在服务器上运行 P2P、BT 或视频流。

需要安装 Python 包时优先使用国内镜像源，例如清华、阿里云、中科大的 PyPI 镜像。国内高校镜像源合集见 <https://mirrors.cernet.edu.cn/>。需要下载数据集时，先在本地下载再上传，或者使用实验室提供的镜像。不要私自配置代理软件。

## 误删或覆盖文件

如果误删了自己或他人的文件，立即停止在该目录继续写入，避免数据被覆盖。然后联系管理员，说明删除的路径、时间和操作命令。不要尝试用来源不明的恢复脚本，也不要在同一块盘上生成大量新文件。

如果文件在 Git、快照或备份中有副本，管理员可以协助恢复。没有副本时，恢复成功率取决于文件系统和后续写入情况。

## 账号或权限问题

账号未开通、密码忘记、需要 `sudo`、需要访问共享目录，都联系管理员。不要在聊天工具里发送密码，也不要把账号借给他人临时使用。
